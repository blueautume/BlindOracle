# 联网恢复与商店验证时序 · 3.0.34 / 60

本版继续使用 AppleVerified 启动流程；联网状态、前台状态和 HTTPS 连通性仅用于安排验证，不是选择 Production/Sandbox 或授予账号权限的证据。

首次启动先给本应用的联网请求完成机会。轻量 HTTPS 预检等待连接；收到合法 HTTP 响应只表示本应用当前能建立网络连接，不依赖正式后端数据库的健康状态，也不证明 App Store 已认证。网络等待不消耗 StoreKit 的快速重试次数。预检无法完成时，仍保留一次受限的 StoreKit 缓存读取机会。

预检使用独立会话的 `waitsForConnectivity`，普通请求等待上限 10 秒、连接等待资源上限 90 秒；离线或联网许可未决时，缓存读取机会可能等到预检退出后才出现。界面说明正在等待联网，并提供系统设置入口。网络路径变化只是恢复信号，不能等同于完整的无线数据授权状态。

系统联网提示、商店认证或其他系统面板使应用暂时失去前台焦点时，不继续耗尽短暂的验证等待预算。重新活跃、网络恢复或预检成功后，协调器在适用的失败状态下受控恢复 shared 读取；自动恢复不会调用 AppTransaction.refresh。用户主动取消和明确的签名、应用、环境或权限拒绝不由前台回调绕过。

自动读取只按应用活跃时间计时；用户主动商店认证保留 60 秒墙钟等待上限，超时后仍保持底层忙碌位。自动恢复最多两轮，主动点击重试才重新开始恢复预算。已观察到的商店内部错误 21 只允许在手动刷新失败后补读一次，不将私有错误码解释为已知网络错误。

3.0.34 为手动 `AppTransaction.refresh()` 返回的 `StoreKitError.userCancelled` 增加一次凭据补读。错误类别不作为用户实际点击取消的证据。应用回到活跃状态且原 SDK 调用真正结束后，仅调用一次 `AppTransaction.shared`；不再主动调用 `refresh()`，也不重复联网预检。补读继续经过原有 verified、应用标识、环境和非空 JWS 校验，只有通过后才能进入账号流程。

取消后的补读次数绑定当前手动验证，不随前后台或网络信号增加。补读失败、再次取消或超时后停止自动恢复；超时调用仍保持串行占用，其迟到结果不会直接放行或触发额外读取。手动认证本身超时后若迟到返回取消，也仅可使用这一份单次补读额度。新的主动重试才开启新的验证轮次。

底层 StoreKit 调用在真正返回前保持占用。显示超时不等于底层工作已结束；旧调用未完成时不启动新的 shared、refresh 或联网预检，也不发送诊断。迟到结果不直接冻结环境，只在适用条件下触发新的、有界的验证。

诊断报告先写入既有受保护的限量队列。进入联网预检或商店验证前，暂停并等待正在发送的诊断结束；应用失去焦点时也停止发送。只有应用稳定活跃且没有验证在途时才允许补报。取消诊断传输不会丢失事件，也不会被当作网络故障增加退避。

本版不更改账号、钥匙串命名空间、额度或购买规则，不切换未知环境，不导入 Sandbox 测试购买额度。模拟验证覆盖授权等待、恢复信号、取消和超时竞态；真实手机的无线数据弹窗与 Apple 商店内部错误仍须通过新 TestFlight 包验证。
